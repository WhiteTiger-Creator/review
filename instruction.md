Repair the Compose Dungeon server in `/app` without adding dependencies or changing the existing `-addr`, `-db`, and `-compose` flags. It must build offline. A Compose service is a room; either `depends_on` form creates two-way doors. Read `dungeon.*` labels from map or `key=value` list form: `entry=true` selects the start, `lock=COLOR` requires `key.COLOR`, `dark=true` blocks looting (not movement) without `torch`, `goal=true` wins, and `items` is a trimmed comma-separated list. Never hardcode the shipped map.

`GET /world` returns 200 with `{"entry":string,"par":integer|null,"route":[string]|null,"rooms":[room]}`; each room is `{"name":string,"exits":[string],"lock":string|null,"dark":boolean,"goal":boolean,"items":[string],"reachable":boolean}`. Sort rooms, exits, and items; empty room lists use `[]`. Compute eventual reachability by repeatedly collecting accessible loot. `par` is the minimum moves to a goal and `route` excludes the entry and is the globally lexicographically smallest shortest winning sequence; both are null when unwinnable. For exits `alcove`, `beacon`, and `cavern`, where alcove is a dead end and the latter two give equal two-move wins, choose `["beacon","vault"]`. `GET /replay` returns 200 with `{"seed":integer,"steps":[string],"won":boolean}`. Start at seed `0x243F6A8885A308D3`, greedily loot the entry before moving, then choose among sorted enterable exits for at most 256 moves and loot after each move; stop on the goal or when no exit is enterable. Each uint64 draw is `state+=0x9E3779B97F4A7C15; z=state; z=(z^(z>>30))*0xBF58476D1CE4E5B9; z=(z^(z>>27))*0x94D049BB133111EB; draw=z^(z>>31)`. For `n` exits, reject draws at or above `2^64-(2^64 mod n)`, then use `draw mod n`.

`POST /sessions` returns 201; `GET /sessions/{id}` and `POST /sessions/{id}/{move,take,undo}` return 200 on success. Move and take bodies are exactly `{"to":string}` and `{"item":string}`; after that one JSON object only whitespace is allowed. A run is `{"id":string,"room":string,"inventory":[string],"moves":integer,"won":boolean}` with sorted inventory and IDs `s%06d`. Errors are `{"error":code}`: check `unknown-session` (404), malformed/extra/missing body fields (`bad-request`, 400), then `unknown-room`, `no-door`, `locked`, `dark`, `no-item`, or `nothing-to-undo` (409). Failed and no-op actions neither mutate nor journal. Keys are reusable; takes are idempotent before dark/no-item checks; loot is private; only successful moves increment `moves`; once true, `won` remains true. Every state-changing move/take journals the exact pre-change run; undo restores it and deletes that newest entry. In bbolt, `sessions[id]` is exact run JSON, `meta["last_id"]` is the decimal counter, and `journal["<id>:<NNNNNN>"]` starts at `000001` per run—never `000000`. Serialize mutations, commit before responding, and restore IDs/undo after restart. Leave an unlocked `/app/data/dungeon.db` containing a winning run.

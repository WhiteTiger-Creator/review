A log-retention daemon decides what happens to each log file it manages: keep it, rotate it, compress it, or delete it outright. The decision is a fixed, deterministic function of the log's service name, its size in megabytes, its age in days, and the host's current disk usage percentage, but the function itself is undocumented and must be recovered by observation.

A copy of the daemon is available at `/opt/retention/decide` for you to query: feed it one log's details as JSON on stdin and it returns the decision. For example, `echo '{"service":"web","size_mb":10,"age_days":5,"disk_pct":40}' | /opt/retention/decide` prints `{"decision":"KEEP"}` or one of the other three actions. You may call it at most 120 times in total; after that every call prints `LIMIT` and exits non-zero. It only exposes this one query interface -- there is no other way to inspect how it reaches a decision. A few worked decisions are in `/app/challenge/examples.json` to show the format.

The audit request set is `/app/challenge/requests.json`: an object with a `requests` array whose entries are `{"id", "service", "size_mb", "age_days", "disk_pct"}`. For every request, decide its action under the real daemon and write `/app/out/decisions.json`, an object with a `decisions` array holding one `{"id", "decision"}` per request, where decision is exactly one of `"KEEP"`, `"ROTATE"`, `"COMPRESS"`, or `"DELETE"`. The request set is far larger than your probe budget, so you must generalize the daemon's behavior from your probes rather than look up every answer. Every decision must be correct. Use any language available in the environment.

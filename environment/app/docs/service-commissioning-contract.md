# Service commissioning publication contract

The operations snapshot is the exact stdout of `/app/bin/catalog-query --batch-file /app/share/service-catalog.batch`. The maintenance snapshot is the exact stdout of the same interface with `HARBOR_CATALOG_DB=/opt/harbor/maintenance-window.db` and `/app/share/maintenance-window.batch`. The raw SQLite files are not operator interfaces.

`/app/var/commissioning-manifest.json` is compact UTF-8 JSON plus one newline. Top-level keys are ordered: `run_id`, `site_key`, `handbook_revision`, `catalog_generation`, `schedule_generation`, `configuration`, `routes`, `assertions`, `window_plan`, `inputs`, `publication`. The top-level `catalog_generation` and `schedule_generation` fields are JSON integers, not strings. Configuration values are strings. Route objects use `method`, `external_path`, `upstream`, `auth_mode`, `timeout_ms`, `source_route_id`, `cohort_code`, `decision_code`. Assertion objects use `name`, `passed`, `observed`, `rule_ref`, with integer `passed=1`.

The nine input records are sorted lexicographically by the pair (`kind`, `path`) and therefore appear in this exact order: `catalog-batch-result` at `/app/share/service-catalog.batch`; `maintenance-window-batch-result` at `/app/share/maintenance-window.batch`; `request-manifest` at `/app/fixtures/requests/replay-set.manifest`; `request:arrival` at `/app/fixtures/requests/arrival-replay.http`; `request:manifest` at `/app/fixtures/requests/manifest-replay.http`; `request:status` at `/app/fixtures/requests/status-replay.http`; `socket-inventory` at `/app/records/socket-occupancy-snapshot.txt`; `socket-open-trace` at `/app/records/socket-allocation-events.txt`; and `window-meta` at `/app/records/window.meta`. Catalog records describe exact stdout bytes; other records describe the named files.

Publication entries are ordered: `/app/etc/harbor-relay/relay.conf`, `/app/etc/harbor-relay/limits.conf`, `/app/etc/harbor-relay/routes.map`, `/app/var/window-plan.json`, `/etc/systemd/system/harbor-relay.service`, `/app/var/commissioning-ledger.db`, `/app/var/commissioning-manifest.json`. Every publication entry is a JSON object whose keys are exactly `path`, `sha256`, `bytes`, `mode`, in that order. The JSON field is named `mode`; `mode_text` is only the corresponding column name in the SQLite `publication_file` table and is not valid in the manifest. The first five entries carry real SHA-256 digests and byte counts. The ledger and manifest use 64 zeroes and byte count 0 to avoid recursive identity. `mode` is the four-character string `0640`, `0644`, or `0600` as appropriate. `/app/var/harbor-commissioning.lock` is required, empty, mode `0600`, and excluded from publication.

A digest-line set writes every lowercase digest followed by `\n`, including the last. `request_set_sha256` uses the request manifest then role files in manifest order. `record_set_sha256` uses `/app/records/window.meta`, `/app/records/socket-allocation-events.txt`, `/app/records/socket-occupancy-snapshot.txt`. The 24-character `run_id` is the first lowercase hex portion of SHA-256 over the pipe-joined sequence: site key, handbook revision, catalog generation, schedule generation, request-set digest, record-set digest, operations snapshot digest, maintenance snapshot digest, readiness digest, relay.conf digest, limits.conf digest, routes.map digest, service-unit digest. No newline is appended.
